# Run contracts

The types in `crates/saci-core` are the shared vocabulary of the CLI, the
backend and the worker. They are serialized as JSON on the wire and in the
database; `schema_version` (currently `1`) marks the run specification and
report formats.

## Identities

| Identity | Form | Notes |
|----------|------|-------|
| Run | `run-<32 hex>` | Generated by the backend on acceptance. |
| Unit key | `1.1`, or `1.1>common/setup.md#2` | The authored ID; units reached through a procedure are prefixed with the invoking unit and the procedure path, so repeated invocations stay distinct. |
| Attempt | `1`, `2`, … | One-based, per unit. Every attempt is kept. |
| Evidence | `ev-<n>` | Run-unique, assigned by the worker in recording order. |
| Event | `seq` 1, 2, … | Contiguous per run. Receivers apply exactly the next `seq`. |

Source locations are `{ "document": "<bundle path>", "line": <1-based> }`.

## Lifecycle and outcome

Lifecycle (`accepted → starting → running → stopping → finished`) and outcome
are separate. Runs only move forward; any non-terminal state may go to
`stopping` or straight to `finished` (for example on a launch failure), and
`finished` is terminal.

Outcomes are `passed`, `failed`, `blocked`, `inconclusive`, `error`,
`skipped` and `cancelled`, with the meanings in the
[execution contract](execution.md#statuses). A run's summary outcome is the
highest of its unit outcomes in the order cancelled, error, failed, blocked,
inconclusive, passed. A skipped unit counts as blocked for the summary, so a
run with unattempted units cannot pass. When the run ends:

- an attempt still in progress is closed as `cancelled` (on cancellation) or
  `error` (any other interruption), and so is its unit;
- a unit that never started becomes `skipped` with the reason;
- cleanup units (a unit or phase whose title mentions cleanup or teardown)
  that did not run are listed in `cleanup_not_run`.

## Assessments

The agent finishes each attempt by submitting an assessment through the
step-assessment tool: an `outcome`, one result per expected criterion
(`criterion` index from 0, `status` `satisfied`, `contradicted` or
`undetermined`, `basis` `mechanical` or `model_judgment`, the `evidence`
ids it relies on, and an `explanation`), and an overall `explanation`.
`saci_core::assessment::validate` rejects a submission, telling the model
every problem so it can resubmit, when:

- the outcome is not `passed`, `failed`, `blocked` or `inconclusive` (`error`,
  `skipped` and `cancelled` are decided by Saci, not the model);
- a criterion is missing, assessed twice or does not exist;
- it cites evidence not recorded in this run, or a `satisfied` or
  `contradicted` result cites none;
- a `satisfied` result with basis `mechanical` cites only evidence that
  holds no answer from the target: an HTTP request with no response (for
  example, connection refused), a shell command that did not finish, an
  MCP call with no result, or a rejected call. A refused connection does
  not show a service is healthy. When the expected result is that the
  call fails, for example a port that must be closed, the model uses
  basis `model_judgment`, and the report shows it as a judgment;
- `passed` has any criterion that is not satisfied; `failed` has none
  contradicted; `blocked` or `inconclusive` has one contradicted or none
  undetermined;
- an explanation is empty.

So a pass needs evidence for every criterion: a printed `PASS` or a zero
exit status is only evidence for the criteria it actually shows. A negative
test passes when its evidence matches the authored expectation, for example
a recorded HTTP 401 for "the request is rejected". `basis` records whether a
result rests on a direct check or on the model's interpretation; Saci
records that claim but does not prove it.

An attempt's outcome is its assessment's outcome, unless an execution error
occurred, which makes it `error`. A unit's outcome is its last attempt's
outcome; earlier attempts stay in the report.

## Events

A worker reports progress as ordered `RunEvent`s (`run_started`,
`attempt_started`, `observation`, `attempt_finished`, `unit_finished`,
`unit_skipped`, `cancellation_requested`, `run_finished`). The backend folds
them into a `RunReport` with `RunReport::apply`, which rejects events for
another run, events out of sequence (including retransmissions), events
after `run_finished`, and unit events that do not match the unit's state:
an attempt outcome that does not follow its assessment, an assessment that
fails the same checks the worker applies (`assessment::validate`: every
authored criterion assessed once, outcome consistent with the criteria,
evidence recorded in the run), a unit outcome other than its last
attempt's, or a skip of a unit that was attempted. Each unit's identity
carries its authored `criteria` for this. A rejected event leaves the
report unchanged.

`attempt_finished` also carries `timing`: `model_requests` (the model
requests sent), `model_ms` (the time spent on model requests, retries
included) and `tool_ms` (the time spent in tool calls). The report keeps it
on the attempt. Use it to find where a run spends its time.

Examples of complete event streams live in
`crates/saci-core/tests/fixtures/runs/` (success, failure with stop, and a
retried-then-cancelled run).

## Secrets

Public types hold secret *references* only: `{ "env": "NAME" }` for a backend
environment variable or `{ "secret": "name", "key": "key" }` for a
Kubernetes Secret. No serializable type has a field for a secret value.
